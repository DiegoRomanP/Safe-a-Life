Testing · Errores de software (1 de 2)

Errores de límites y de carrera

Boundary errors

Errores de límites

Qué es: el código falla justo en el borde de lo permitido.

Ejemplo simple: un formulario que acepta una edad de −1 o de 200.

En el proyecto: la ubicación debe tener máximo 3 decimales y estar dentro de Lima. Sin control, una latitud −12.0461 o un punto en otra región llegarían a guardarse.

Solución: la regla vive en el dominio (location.ts) y la API responde 422; el mapa rechaza puntos fuera de Lima; 16 pruebas cubren los bordes.

Race conditions

Condiciones de carrera

Qué es: el resultado depende del orden en que llegan dos acciones al mismo tiempo.

Ejemplo simple: un doble clic en «Pagar» que cobra dos veces.

En el proyecto: al cerrar sesión, una respuesta lenta llegaba después y volvía a abrirla; y dos lotes pedidos a la vez podían pasar el tope por administrador.

Solución: un contador de «época» descarta respuestas viejas (session.ts:15); el tope se recomprueba con un bloqueo en la base y cada acción lleva Idempotency-Key.

Testing · Errores de software

Ambos tipos están en la lista «Software Errors» de la clase. Límites: es la regla que muestra la prueba de location.test.ts. Carrera: el arreglo de la sesión está en el commit 725ce19 (restoreSession con época) y el del tope de lotes en 6164c2b (se vuelve a comprobar bajo el bloqueo de la cuota). La Idempotency-Key hace que un reintento o un doble envío no repita la acción.

Testing · Errores de software (2 de 2)

Errores de interfaz y de configuración

User interface errors

Errores de interfaz

Qué es: la pantalla se ve o se comporta mal aunque los datos sean correctos.

Ejemplo simple: un botón que queda tapado por otro elemento.

En el proyecto: al cambiar de sección en Edge, la página «saltaba» 7 px porque la barra de scroll aparecía y desaparecía según el largo de la vista.

Solución: una línea de CSS, scrollbar-gutter: stable, reserva siempre el espacio de la barra (PR #37).

Versioning and configuration errors

Errores de versión y configuración

Qué es: el código es correcto, pero falla por el entorno o la configuración.

Ejemplo simple: «en mi PC funciona, en el servidor no».

En el proyecto: 2 pruebas pasan en Linux y fallan en Windows por los permisos de archivo; y en local nadie podía entrar porque el límite de 10 logins por IP lo compartían todos.

Solución: el CI corre en Linux, igual que el servidor; en local se vacían los contadores y el límite quedó documentado.

Testing · Errores de software

El error de interfaz lo encontró un usuario probando en Edge y se midió con el navegador: el título se movía de 289 a 296 px. Las pruebas de Windows esperan permisos 0700 de Linux y reciben 0666. El límite de logins protege la API en producción, donde cada persona tiene su propia IP; en local todos salen desde 127.0.0.1.

Patrón estructural · Implementado

Facade: una sola puerta hacia el backend

Problema: cada llamada al backend debe armar cabeceras, Idempotency-Key, CSRF, cookies y traducir errores.

Solución: apiRequest esconde todo eso. Las pantallas usan una sola función.

frontend/src/lib/api/http.ts:34

// Lo que oculta la fachada

export async function apiRequest(method, path, options) {

  headers['Idempotency-Key'] = … // sin duplicados

  headers['X-CSRF-Token'] = csrfToken // sesión

  fetch(`/api/v1${path}`, { credentials, no-store })

  if (!ok) throw new ApiError(tipo, status, code)

}

 

// Lo que ve una pantalla

apiRequest('PUT', '/donors/me/onboarding-profile', { body })

Patrones · Facade

Facade da una interfaz simple a un subsistema complejo. apiRequest concentra seis responsabilidades: Content-Type, Idempotency-Key reutilizable en reintentos, token CSRF, cookies sin caché ni referrer, errores de red y traducción del error HTTP a ApiError. Si cambia cómo se manda el CSRF, se cambia en un solo lugar.

Patrones · Próximos

Builder: los seis correos usan compose(asunto, párrafos, enlace, extras), donde hay que recordar el orden y pasar null. Abstract Factory: hoy el enviador y la lista de destinatarios se eligen con dos condiciones distintas; si se agrega un proveedor y se olvida la segunda, se enviaría sin la lista de seguridad. Prototype se evalúa aparte.

Cookie: __Host-sal_at=… ③ sesión

X-CSRF-Token: … ③ seguridad

Content-Type: application/json

① URL = recurso con sustantivos («me» = mi hospital) · ② PATCH = cambiar una parte · ③ sesión en cookie + CSRF · ④ si se repite, no se duplica · ⑤ solo lo que cambia

  "status": "activa", … } }

{ "error": { "code": "STATE_CONFLICT",

API REST · Petición completa

Ejemplo real del contrato (operación transitionOwnHospitalNeed, con los ejemplos de docs/openapi.json). Publicar una necesidad es cambiar su estado a activa: no existe una ruta /publicar. Éxito y error usan siempre la misma envoltura: data o error. En todo el contrato hay GET 37, POST 24, PATCH 9, PUT 2 y DELETE 2. El 409 aparece, por ejemplo, si se intenta activar una necesidad ya cerrada.

API REST · docs/openapi.json (resumido y comentado)

Así define el contrato esa misma petición

"/api/v1/hospitals/me/needs/{needId}": { // ruta

  "patch": { // método

    "operationId": "transitionOwnHospitalNeed",

    "security": [{ "sessionCookie": [], // sesión

               "csrfToken": [] }], // y CSRF

    "parameters": [ "IdempotencyKey" ], // cabecera

    "requestBody": { // qué se envía

      "schema": "NeedTransitionRequest",

      "example": { "status": "activa" } },

    "responses": { // qué vuelve

      "200": "NeedEnvelope", // éxito

      "409": "Conflict", … } } } // errores

// el cuerpo permitido

"NeedTransitionRequest": {

  "required": ["status"],

  "status": { "enum": ["activa",

    "cerrada", "cancelada"] },

  "additionalProperties": false

}

Un estado que no está en la lista, o un campo de más, se rechaza antes de llegar a la lógica.

De este archivo salen los tipos de TypeScript, la validación del backend, el mock Prism y la colección Bruno. El CI falla si el código se desalinea.
