El problema
Jhan Leiva

Un hospital necesita sangre: ¿a quién avisar, rápido y sin exponer datos?

Qué hace

  • El hospital publica lo que necesita.
  • El sistema filtra candidatos: grupo compatible, disponibles y cerca (preselección).
  • Les avisa por correo y ellos responden.

Qué no hace

  • No guarda pacientes ni historias clínicas.
  • No decide si alguien es apto para donar: eso lo evalúa el hospital.
  • Responder «sí» es solo intención de asistir.

Para la demo

  • Lima, Perú.
  • 3 hospitales y hasta 500 donantes.
  • Todos los datos son inventados.
Idea clave: el sistema sí filtra (preselecciona por grupo compatible, disponibilidad y distancia), pero no evalúa la aptitud médica: el grupo es el que declaró la persona y el hospital lo verifica. Recalcar que confirmar no es una cita ni significa que la persona pueda donar: el hospital lo verifica. Si preguntan por qué datos inventados: porque grupo sanguíneo y ubicación son datos sensibles; usar datos reales exige revisión legal (Ley 29733).

Las 3 cifras prueban la decisión: un solo despliegue, 7 módulos con límites claros y reglas independientes (por ejemplo, la compatibilidad de grupos es una función pura con sus propias pruebas). Si preguntan qué es un módulo: una carpeta con todo lo de un tema (por ejemplo «necesidades»), que no mete mano en las demás.

El contrato en el centro

openapi.json describe cada operación; front y back lo siguen.

Pantallas por rol

Donante, hospital y superadmin tienen su propia carpeta.

Contrato (OpenAPI): un archivo que dice «para crear una necesidad envía estos datos y recibirás esta respuesta». Así front y back no se contradicen. Dentro de cada módulo hay 4 capas: dominio (reglas), aplicación (casos de uso), http (rutas) e infraestructura (conexión con Supabase/Resend).

La idea base: piezas con enchufes

El problema

Si las reglas del negocio llaman directo a Supabase o a Resend, cambiar de proveedor obliga a reescribir todo.

La solución: «puertos y adaptadores»

Las reglas hablan con un enchufe (una interfaz). Detrás del enchufe se conecta el servicio real o uno de prueba.

ReglasDominio«¿Este donante es compatible?»
EnchufePuertoEmailSender, NeedsRepository
ConectorAdaptadorTraduce a Resend o a Supabase
ServicioExternoResend, Supabase o uno falso

Los patrones del curso Factory, Adapter y Strategy son justamente las piezas que hacen funcionar esta idea.

Analogía: un cargador de celular. El celular (las reglas) solo conoce el puerto USB-C; el adaptador de pared se cambia según el país (Resend, Supabase o un falso para pruebas). A esto también se le llama «arquitectura hexagonal».

Factory, Adapter y Strategy en el código

Factory
shared/persistence/supabase-client.ts
interface SupabaseFactory {
  forUser(token): Client;
  anonymous(): Client;
}

// quien la usa solo pide:
const client = token
  ? factory.forUser(token)
  : factory.anonymous();

Decide qué conexión crear; el resto del código no lo sabe.

Adapter
email-delivery/.../resend-sender.ts
// nuestro «enchufe»
interface EmailSender {
  send(message);
}

// el adaptador para Resend
function createResendSender() {
  return { send: (m) =>
    fetch('api.resend.com', …) };
}

Traduce nuestro «enviar» al formato de Resend.

Strategy
backend/src/composition-worker.ts
const sender =
  provider === 'resend'
    ? createResendSender()
    : new FakeEmailSender();

// el resto usa sender.send()
// sin saber cuál es

Dos estrategias intercambiables según el entorno.

Señalar en cada bloque: Factory → «la fábrica decide». Adapter → «traduce». Strategy → «se elige una u otra y el resto no cambia». Si preguntan la diferencia entre Adapter y Strategy: Adapter traduce una interfaz a otra; Strategy elige entre varias implementaciones de la misma interfaz. Aquí se combinan: Resend entra por un adaptador y es una de las estrategias.

Observer y Decorator en el código

Observer · parcial
backend/src/app.ts · server.ts
// se suscribe al «terminó la respuesta»
res.on('finish', () => registrar(res.statusCode));

// se suscribe al «apágate»
process.on('SIGTERM', () => server.close());

Sujeto: la petición y el proceso. Observadores: el registro y el cierre ordenado. Además, Resend nos avisa por webhook cuando un correo se entregó.

Decorator · parcial
platform/http/health.router.ts
// envuelve una tarea y le agrega un límite
function withTimeout(tarea, ms) {
  return Promise.race([tarea, esperar(ms)]);
}
// la tarea original no cambia

Idea: agregar comportamiento envolviendo. Igual hace requestLogger: envuelve cada petición para registrarla.

Webhook = Resend llama a nuestra API para avisarnos algo (como una notificación). Si preguntan por qué no hay clases Observer/Decorator: Node ya trae el mecanismo de eventos y las funciones que envuelven; crear clases encima sería código extra sin beneficio.
Seguridad
Roman Palomino

Cuatro barreras para proteger datos sensibles

1Sesión protegidaSe guarda en una cookie que el navegador no deja leer a ningún script.
2Verificación en dos pasosHospital y superadmin usan un código extra; lo delicado lo pide otra vez.
3El rol lo decide el servidorNunca se confía en lo que envía el navegador.
4La base filtraCada hospital solo puede ver sus propios datos.

Además

  • El enlace del correo se borra de la barra de direcciones.
  • Todo queda auditado, sin datos personales.
  • Revisores independientes de seguridad aprobaron los cambios.
Nombres técnicos por si los piden: (1) cookie HttpOnly + token CSRF, que evita que otra página actúe en tu nombre; (2) MFA y step-up; (3) el rol sale de la membresía guardada; (4) RLS, seguridad a nivel de fila en PostgreSQL.

Conclusiones

1 · La arquitectura se ajusta al proyecto

Un monolito modular fue suficiente para un equipo pequeño y una demo de 3 hospitales, sin cerrar la puerta a crecer.

2 · Los patrones resolvieron un problema real

Factory, Adapter y Strategy nos dejan cambiar la base de datos o el correo, o usar datos de prueba, sin reescribir las reglas.

3 · Con datos de salud, la privacidad va primero

Diseñarla desde el inicio, en cada capa, es más fácil que agregarla al final.

4 · El avance es verificable y lo pendiente está claro

Más de 1000 pruebas y revisiones respaldan lo hecho; faltan las invitaciones, el login por rol y conectar todo.
